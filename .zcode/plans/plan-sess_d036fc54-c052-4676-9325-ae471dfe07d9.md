# CRUD 补齐实施计划

## 目标与边界
补齐三实体(食材/菜品/用户)的 CRUD 缺口:**硬删除、按 id 的单查与通用字段更新、用户自助资料维护、管理员用户管理**。已确认决策:删除=硬删除(无 schema 迁移);内容写权限=登录后本人或 admin。**既有 name 定位的审核接口与 review.html 契约一律不动**;`status` 字段不进通用更新(审核状态仍走既有 `/api/status`、`/api/dish/status`);用户内容创建流程仍留下一期。

## 1. 仓储层 `shike/repository.py` 新增(沿用现有 connect+try/finally+DictCursor+动态字段拼接风格)
- `find_ingredient_by_id(id)` / `find_dish_by_id(id)` → dict|None,含 `id/user_id/status` 与全部业务字段(菜品含 `image`)
- `update_ingredient(id, fields)` / `update_dish(id, fields)` → bool,白名单动态 SET(菜品白名单含 `image`)
- `delete_ingredient(id)` / `delete_dish(id)` / `delete_user(id)` → bool(DELETE 语句)
- `list_users()` → list[dict] 按 id 升序
- `update_user(id, fields)` → bool,白名单 nickname/status/role/password_hash
- `user_owns_content(user_id)` → bool(ingredient+dish 两表 COUNT)

## 2. Web 层 `web/app.py` 新增端点
**内容读**:公开;私有内容(user_id 非空)仅本人/admin 可见,他人 404。
- `GET /api/ingredients/<id>`、`GET /api/dishes/<id>`

**内容写**(require_login;官方库内容仅 admin,私有内容仅本人或 admin):
- `PATCH /api/ingredients/<id>` — 部分更新,合并现有行后整体跑 `validate_ingredient`(它天然吃数据库行形状);400 返回错误列表;改 name 撞 `uk_name` 409;404 未命中
- `DELETE /api/ingredients/<id>`、`DELETE /api/dishes/<id>` — 硬删除
- `PATCH /api/dishes/<id>` — 白名单 `_DISH_FIELDS`+`image`,轻校验(未知字段拒绝、字符串类型、长度上限按列宽、category ∈ 菜品分类词表、solar_terms ∈ 节气词表且升序)

**用户管理**(require_admin,`_user_view` 脱敏复用):
- `GET /api/users` — 列表
- `PATCH /api/users/<id>` — 白名单 nickname/status/role;值域校验(正常/禁用、user/admin);禁止管理员禁用自己或把自己降级为 user(400)
- `DELETE /api/users/<id>` — 名下有食材/菜品则 409(提示改用禁用),否则硬删

**自助**:`PATCH /api/auth/me`(require_login)— nickname(≤50 字)/password(≥6 位且必须携带 `current_password` 并验证通过,否则 400)。

权限辅助:`_can_write(row)` = `g.current_user.role=="admin"` 或 `row["user_id"]==g.current_user["id"]`。

## 3. 测试(沿用 monkeypatch repository 函数的既有惯例)
- `tests/test_web_crud.py`:无令牌 401、非 admin 改官方内容 403、本人改自己私有内容成功、校验失败 400、改名冲突 409、未命中 404、硬删除成功、私有内容对他人 404
- `tests/test_web_users.py`:非 admin 访问用户管理 403、admin 列表脱敏、改状态/角色、自禁/自降 400、删除有内容用户 409、自助改昵称、自助改密码(缺/错 current_password 400,正确后新密码可登录)
